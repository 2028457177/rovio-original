第一部分 · 项目总览

1.1 这是什么

Rovio —— 基于 微服务 + Supervisor-Worker 多智能体编排 的自动化办公助手。用户一句话触发「规划 → 多 Agent 并行执行 → 反思修订 → 汇总」的完整工作流，集成 RAG 知识库、联网搜索、代码沙箱、网页抓取、Word 文档生成/填充、产物管理、长期记忆，全程 SSE 流式可观测。

架构演进：旧版是 Streamlit + SupervisorAgent + ReactAgent 两层单体（app.py/fastapi_app//react_agent.py，已废弃），后演进为单体 FastAPI（库 agent_records），最终拆分为现在的 6 微服务 + AIRAGAgent 引擎包 形态。langgraph.json 是历史保留，不再是运行入口。

第二部分 · AIRAGAgent/agent —— 智能体编排核心（最重要）

这是整个项目的心脏。核心范式是 Planner → Executor → Reflector → Finalizer 四阶段，由 Orchestrator 一个类驱动。

2.1 orchestrator.py —— Supervisor 主循环

职责：把用户请求拆成 Plan、调度 SubAgent 执行、反思修订、流式汇总答案，全程产出 SSE 事件。

关键数据模型（Pydantic）

名称 定义 作用
StepSpec (L59) description / subagent / depends_on Planner 产出的单步规约，depends_on 是 step_idx 列表（从 0 开始）
PlanSpec (L73) goal / steps 完整计划规约
Reflection (L79) action / feedback 反思结果，action ∈ accept / retry / revise / ask_user

主入口 execute_stream（L731-822）三段式

def execute_stream(self, query, chat_history, user_id, session_id):
    # 1) 规划
    plan_gen = self._plan_stream(query, chat_history, user_id)
    while True:
        try:
            chunk = next(plan_gen); yield chunk          # 思考过程逐个透传
        except StopIteration as e:
            spec = e.value; break                        # generator 返回值 = PlanSpec
    plan = self._build_plan(spec, user_id, session_id)   # 落库 plans + plan_steps
    yield {"type": "plan_created", ...}

    # 2) 执行 + 反思主循环
    while not plan.is_all_done():
        ready = plan.get_ready_steps()                   # 依赖感知调度
        if len(ready) == 1:
            result = yield from self._execute_step(plan, ready[0], ...)
            reflection = self._reflect(...)
            # accept / retry(≤1) / revise(≤2, continue 重进循环) / ask_user
        else:
            yield from self._execute_steps_parallel(plan, ready, ...)  # 并行批次

    # 3) 汇总
    final_text = yield from self._finalize(plan, query, llm)
    yield {"type": "plan_completed", ...}

next() + StopIteration.value 是「generator 既流式又返回值」的经典技巧——_plan_stream 一边 yield 思考事件，一边把解析好的 PlanSpec 通过 return 带回来。

Planner：_plan_stream（L290-339）

  • 用 llm.stream() 逐 chunk 处理：从 chunk.additional_kwargs["reasoning_content"] 取 DeepSeek thinking 推理过程 yield thinking 事件；正文累加后 _extract_json + json.loads + PlanSpec(**data)。
  • 有意不用 with_structured_output（L255 注释）：DeepSeek thinking 模式不支持 tool_choice。这是全项目最重要的兼容性取舍——Planner 输出是纯文本 JSON，靠 _extract_json（L169）容错提取（去 `` 围栏、取第一个{到最后一个}`）。
  • 规划前 _recall_relevant_memory（L231）召回 10 条长期记忆注入上下文，失败静默降级；_format_history（L217）只取最近 6 条历史、每条截 200 字。
  • Planner 失败兜底：PlanSpec(goal=query, steps=[StepSpec(subagent="")])——退化为单步直接回答。

Executor：_execute_step（L361-462）

token_plan = current_plan_id_var.set(plan.id)        # 三个 artifact ContextVar
token_session = current_session_id_var.set(plan.session_id)
token_step = current_step_idx_var.set(step.step_idx)
# ... finally 里逐个 reset(token)，早退分支也手动 reset，不泄漏
  • increment_attempts=bool(feedback)：带反馈重跑才累加 attempts，首次执行不算。
  • 前序结果注入：task_desc += self._build_step_context(plan, exclude={step.step_idx})。
  • 两条执行路径： 1. subagent 为空 → Orchestrator LLM 直接回答。单步 plan 用旧协议事件名 thinking/output，多步用 step_thinking/step_output（前端兼容设计）；单步时用原始 query 而非 step.description 作 HumanMessage（Planner 改写会偏语义）。 2. subagent 非空 → SubAgentRunner(sub, llm) 每次新建实例，runner.execute_stream 事件改写成 step_* 透传。
  • 结果 [:65000] 截断写库（匹配 MySQL TEXT 65535 字节上限），_save_step_result 落盘 tasks/<plan_id>/plan_results/step_<idx>.md，yield step_completed。
  • 异常不抛出：单步失败写 FAILED + yield step_failed + return 空串，主循环继续跑后续步骤。

并行执行：_execute_steps_parallel（L464-514）

  • 只有 all(s.subagent for s in steps) 才真并行；混有直接回答步则退化串行。
  • 并行时故意不设 step_idx ContextVar（L472 注释），每个 spec 的 description 注入 _build_step_context(plan, exclude=batch_indices)——排除整个并行批次，因为批次内步骤彼此独立、不应互相引用结果。
  • 并行步不逐个反思（太慢），只对失败步不调 LLM 直接重试一次。

Reflector：_reflect（L589-622）

两条短路： - subagent 为空 → 直接 accept； - FAILED 步若 attempts <= MAX_RETRIES(=1) → 直接 retry（不调 LLM），否则 accept 防死循环。

正常路径把 step.result[:2000] 喂给 Reflector LLM，解析失败默认 accept。约束：MAX_RETRIES=1、MAX_REVISIONS=2。

Finalizer：_finalize（L657-725）

  • 单步直接回答的 plan 不二次加工（output 已在执行时流式推送过）。
  • 全失败 → 直接输出失败话术，plan 置 FAILED。
  • 部分/全部成功 → 每步 result[:1500] 拼 summary 让 Finalizer LLM 整合，流式 yield；流式失败 fallback 直接拼接各步结果。

2.2 plan.py —— Plan 数据模型与持久化

  • 状态枚举：PlanStatus（planning/executing/reflecting/completed/failed/revised/cancelled）、StepStatus（pending/ready/running/completed/failed/skipped/blocked）。注意 READY 定义了但从不落库（ready 是计算出来的）。
  • plan_id = f"plan_{毫秒时间戳}_{uuid前6位}"；depends_on 在 DB 里存逗号分隔字符串，from_row 解析回 int 列表。

get_ready_steps（L143-158）—— 依赖解析核心

completed_idxs = {s.step_idx for s in self.steps if s.status == COMPLETED}
failed_idxs    = {s.step_idx for s in self.steps if s.status in (FAILED, BLOCKED)}
for s in self.steps:
    if s.status != PENDING: continue
    if all(dep in completed_idxs for dep in s.depends_on):
        ready.append(s)                        # 同批返回多个 = 并行批次
    elif any(dep in failed_idxs for dep in s.depends_on):
        s.status = BLOCKED                     # 有副作用的 getter！

坑：BLOCKED 只改内存，主循环负责持久化（orchestrator 已配合处理）。

CRUD 要点

  • create_plan：cursor.lastrowid 回填 step.id。
  • update_step_status：动态拼 SET；running 写 started_at，终态写 finished_at；attempts = attempts + 1 原子自增。
  • replace_plan_steps：修订时整体 DELETE 再 INSERT（不留旧步历史），plan 重置为 executing。
  • get_session_plan：ORDER BY (status IN ('planning','executing',...)) DESC, created_at DESC——布尔表达式排序，优先取未完成 plan。

2.3 sub_agent.py —— SubAgent 体系

SubAgent dataclass（L32-75）

@dataclass
class SubAgent:
    name: str; description: str; tools: list
    system_prompt: str; workflow_hint: str
    max_tool_calls: int = 20
    category: str = "domain"

    def build_agent(self, llm=None):
        return create_agent(
            model=llm or chat_model,
            system_prompt=identity + self.system_prompt,
            tools=self.tools,

        )

每次调用新建独立 agent 实例——这是线程安全的关键。

SubAgentRunner.execute_stream（L111-195）

  • 与旧 ReactAgent 流式协议完全一致（thinking/thinking_end/output），Orchestrator 可无缝替换。
  • runtime_context["active_skills"] = [sub_agent.name] 注入，供 smart_prompt_switch 中间件识别当前激活的 SubAgent。
  • stream_mode="messages" + context=runtime_context；except TypeError 回退不带 context 的调用（兼容旧 langchain 的防御写法）。
  • 兜底（L191-195）：调了工具但没有任何可见 output 时，把所有工具结果拼成列表补发 output——防止 agent 只调工具不总结导致前端空白。

run_steps_parallel（L271-333）—— 全项目最精妙的并发细节

parent_ctx = contextvars.copy_context()       # 主线程捕获快照（user_id/ip/plan_id...）
def _run_one(spec):
    child_ctx = parent_ctx.copy()             # 每个 worker 复制独立副本！
    child_ctx.run(_inner)                     # 在副本里跑流式消费

为什么不能直接共享 parent_ctx：Context 对象非线程安全，多线程共享同一个 Context.run() 会报 "already entered"。每个 worker 必须 .copy()。ThreadPoolExecutor(max_workers=min(5, len(specs)))，as_completed 收集后按 step_idx 排序保证输出稳定；单步异常包装成 success=False 不炸批次。

4.3 chat_service（:8003，lc_chat）—— 核心服务

main.py：POST /api/chat 处理流程

  1. 手动解析 client_ip（X-Real-IP → X-Forwarded-For → client.host）。

        loop.call_soon_threadsafe(queue.put_nowait, chunk)   # 跨线程安全入队
    loop.call_soon_threadsafe(queue.put_nowait, SENTINEL)
loop.run_in_executor(None, lambda: ctx.run(sync_producer))

三个要点： - loop.call_soon_threadsafe(queue.put_nowait, item)：工作线程不能直接 await queue.put，把入队调度回事件循环线程——线程→asyncio 的标准桥。 - ctx.run(sync_producer)：保证工作线程里 user_ip_var.get() 等读到请求上下文。 - 哨兵 + 错误透传：异常也入队，消费侧 isinstance(item, Exception) 时置错误标记并 raise，埋点能记录失败。

finally 埋点：无论正常/异常/断连，算 duration_ms + 粗估 tokens（中文 1 字 = 1 token，其余 4 字符 = 1 token）→ log_api_call 写 lc_chat → publish_event(CHANNEL_CHAT_COMPLETED) 发 admin。埋点自身再套 try/except。

会话持久化：支持 truncate_to 历史回滚；结束后 save_message 写 user/assistant 两条 + 回写 Redis 缓存 + 补发 message_ids 事件（前端用于反馈/分叉）。

天然支持多会话并发流式——A 会话还在生成时切到 B 会话，A 的流在后台继续跑。

sendMessage 流程要点

  1. 防重入：同一会话流式中禁止再发。
  2. push user 消息 → 自动标题（首条前 30 字，除非用户手动改过）→ bump 置顶。
  3. push reactive assistantMsg 占位 {streaming:true, plan:null, steps:{}}。
  4. markRaw(new AbortController())——markRaw 避免 Vue 对 controller 做响应式代理。
  5. 首次发送用 navigator.geolocation 拿经纬度（10s 超时，失败缓存不再重复请求）。
  6. onMessageIds 把后端真实消息 id 存到 dbId 字段而非覆盖 id——覆盖 id 会让 v-for :key 变化导致组件重挂载，"流式结束后内容短暂消失再出现的闪烁"。
  7. onEvent 里是 step 状态机：plan_created 初始化每 step 的 {status:'pending', thinking:'', output:''}；step_started → running；step_thinking/output 增量追加；step_completed → done；step_failed → failed。

前后端历史一致性

  • regenerateMessage(assistantMsg)：向前找最近的 user 消息作为问题（否则 [U1,A1,U2,A2] 重生成 A1 会错把 U2 当问题）。
  • regenerateFromUserIndex / editAndResend：本地 splice 截断 + truncate_to 发后端同步回滚，前后端上下文一致。

防丢失三件套

  1. 模块级单例防路由切换丢失；
  2. loadConversations 单次加载保护 + 先把正在流式的本地会话摘出来，后端数据填充后再覆盖回去——防后端旧数据覆盖进行中内容；
  3. resetChatState() 登出/注销/登录时 abort 全部流并清空——防串号看到上一个用户的会话。

第七部分 · 贯穿全局的十大设计精髓（复习重点）

  1. ContextVar 链：FastAPI 注入用户上下文（user_id/ip/lat/lon）→ Orchestrator 注入计划上下文（plan_id/session_id/step_idx）→ 工具层消费；并行时 copy_context().copy() 跨线程传递（Context 非线程安全，直接共享报 "already entered"）。
  2. 同步生成器 → 异步 SSE 桥：asyncio.Queue + loop.call_soon_threadsafe(queue.put_nowait, item) + ctx.run(sync_producer) + SENTINEL 哨兵。
  3. db_patch 零侵入重定向：_conn.mysql_conf["database"] = DB_NAME 原地改字典，几千行引擎代码零改动落到微服务库。
  4. generator 既流式又返回值：next() 循环 + StopIteration.value 取 PlanSpec。
  5. 多知识库隔离三处落地：MySQL 按 owner_user_id/scope、Chroma 按 kb_id 元数据 filter（单集合 kb_store）、Redis 缓存键内嵌 u{uid}|k{sig} 签名。
  6. 事件驱动统计：chat 生产 → Redis Pub/Sub → admin 消费落库，lc_admin 三表是最终一致副本，统计查询不打业务库。
  7. 降级哲学（可用性 > 一致性）：Redis 挂了缓存/限流/队列全部静默放行或跳过；埋点写库失败吞异常；kb 播种失败不阻断启动；嵌入切换自动清库重建自愈。
  8. JWT 共享密钥独立验签：不查库不回调 auth；Bearer + ?token= 双通道（SSE/img 场景）；/internal/* 无鉴权靠内网拓扑隔离（唯 model-config 带 X-Internal-Call 头，因为返回明文 api_key）。

第九部分 · 一条请求的完整生命周期（串线复习）

以「用户问：帮我查下北京天气，写进 Word 报告」为例：

  1. 前端 ChatInput → useChat.sendMessage → push user 消息 → api/chat.js fetch POST /api/chat（Bearer + 经纬度）。
  2. chat_service/main.py：解析 IP → set 4 个 ContextVar → ZSET 滑动窗口限流 → StreamingResponse。
  3. chat_service/agent.py：copy_context() → 线程池跑 Orchestrator.execute_stream → call_soon_threadsafe 入队 → 消费侧逐 chunk yield SSE。
  4. Orchestrator：召回长期记忆 → Planner 流式思考（前端 thinking 面板实时滚动）→ 解析 JSON 出 2 步计划（step0 weather 查天气；step1 wordgen 写报告，depends_on=[0]）→ 落库 plans/plan_steps → yield plan_created。
  5. Executor：step0 ready → SubAgentRunner(weather) → create_agent + 中间件链 → get_user_location/get_city_code/get_weather（工具内 user_lat_var.get() 读 GPS）→ 结果落盘 plan_results/step_0.md → Reflector accept。
  6. step1 依赖满足 → wordgen 执行（任务描述里注入了 step_0.md 路径+摘要）→ run_word_code 子进程 cwd=tasks/<plan_id>/ → 读前序结果 → WordDoc 排版 → doc.save → create_artifact 注册产物。
  7. Finalizer 汇总两步结果流式输出 → yield plan_completed。
  8. agent.py finally：save_message 落库两条 + 回写 Redis 缓存 + 发 message_ids → 埋点 log_api_call + publish chat.completed。
  9. admin_service：订阅到事件 → INSERT lc_admin.api_call_logs（看板 DAU/趋势数据源）。
  10. 前端：step 状态机驱动 PlanPanel 实时渲染 → 全量 output 覆盖 assistantMsg → onDone 持久化会话。
